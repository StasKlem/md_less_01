# Системный дизайн мобильных приложений: Полное руководство по архитектуре и инфраструктуре

## Введение

Системный дизайн для мобильных приложений (Mobile System Design) — это дисциплина, занимающаяся проектированием масштабируемых, надёжных и производительных мобильных систем. В отличие от веб-разработки, мобильная разработка сталкивается с уникальными ограничениями: нестабильное сетевое соединение, ограниченная ёмкость батареи, разнородность устройств (fragmentation), ограниченный объём памяти и процессорного времени.

Цель данного документа — предоставить исчерпывающее руководство по архитектурным решениям, используемым при создании современных мобильных приложений для платформ iOS и Android. Документ охватывает клиентскую архитектуру, сетевой слой, локальное хранение данных, стратегии синхронизации, безопасность и взаимодействие с бэкендом.

## Глава 1. Архитектурные паттерны клиентской части

Выбор архитектуры определяет тестируемость, поддерживаемость и масштабируемость кода. В мобильной разработке доминируют три основных подхода.

### 1.1. MVVM (Model-View-ViewModel)
MVVM является стандартом де-факто для iOS (с SwiftUI/UIKit) и Android (с Jetpack Compose/XML).
- **Model:** Содержит бизнес-логику и данные. Не знает о существовании View.
- **View:** Отвечает только за отображение UI. Наблюдает за изменениями в ViewModel.
- **ViewModel:** Хранит состояние UI (State), обрабатывает действия пользователя и взаимодействует с Model.

**Преимущества:**
- Чёткое разделение ответственности.
- Упрощённое модульное тестирование ViewModel.
- Легкая привязка данных (Data Binding).

**Недостатки:**
- ViewModel может разрастаться («God Object»), если в неё сваливать всю бизнес-логику.
- Требует механизма реактивного программирования (Combine, RxSwift, Flow, LiveData).

### 1.2. Clean Architecture
Чистая архитектура предлагает деление на слои:
- **Presentation Layer:** UI и ViewModel.
- **Domain Layer:** Чистая бизнес-логика (Use Cases / Interactors). Не зависит от фреймворков.
- **Data Layer:** Репозитории, реализующие интерфейсы Domain слоя. Содержит работу с API и БД.

**Принцип зависимостей:** Зависимости направлены внутрь. Domain слой не знает о Data слое.
**Применимость:** Крупные enterprise-приложения, где бизнес-правила сложны и могут использоваться на разных платформах (iOS, Android, Web).

### 1.3. MVI (Model-View-Intent)
Популярный паттерн в реактивном программировании.
- **Intent:** Намерение пользователя (например, кнопка «Купить»).
- **Model:** Уникальное состояние экрана (State).
- **View:** Рендерит состояние.

**Ключевая особенность:** Однонаправленный поток данных (Unidirectional Data Flow). Состояние неизменяемо (Immutable). Любое действие создаёт новое состояние.
**Плюсы:** Предсказуемость состояния, легкая отладка (можно логировать поток состояний).
**Минусы:** Высокий порог входа, избыточность для простых экранов.

## Глава 2. Сетевой слой и взаимодействие с API

Сеть — самое узкое место мобильного приложения. Дизайн сетевого слоя должен учитывать задержки, потери пакетов и лимиты трафика.

### 2.1. Протоколы передачи данных
1.  **REST over HTTP/2:**
    -   Стандарт для большинства приложений.
    -   Использует JSON для сериализации.
    -   Stateless: каждый запрос содержит всю необходимую информацию.
    -   **Оптимизация:** Использование HTTP/2 позволяет мультиплексировать запросы, снижая задержки (head-of-line blocking решён на уровне протокола).

2.  **GraphQL:**
    -   Позволяет клиенту запрашивать только нужные поля.
    -   Решает проблему over-fetching (получение лишних данных) и under-fetching (необходимость делать несколько запросов).
    -   **Минусы:** Сложнее кэшировать на уровне HTTP, выше нагрузка на сервер при сложных запросах.

3.  **gRPC (Protobuf):**
    -   Бинарный протокол на основе HTTP/2.
    -   Идеален для микросервисной архитектуры и внутренних коммуникаций.
    -   **Плюсы:** Строгая типизация, высокий размер payload (меньше вес, чем JSON), стриминг данных.
    -   **Минусы:** Человеко-не читаемый формат, требует генерации кода.

### 2.2. Стратегии опроса и обновлений
-   **Polling (Опрос):** Клиент регулярно запрашивает данные (например, каждые 30 секунд).
    -   *Проблема:* Разряд батареи, лишние запросы, если данные не изменились.
-   **WebSockets:** Постоянное соединение для двусторонней связи.
    -   *Использование:* Чаты, уведомления в реальном времени, биржевые котировки.
    -   *Риск:* Удержание соединения в фоне может быть ограничено ОС (iOS suspend background tasks).
-   **Push Notifications (APNs/FCM):** Сервер инициирует сообщение.
    -   *Лучшая практика:* Пуш содержит только метаданные («пришло новое сообщение»), приложение подгружает тело сообщения при открытии.

### 2.3. Обработка ошибок и повторные попытки (Retry Policy)
Сеть нестабильна. Необходимо реализовывать экспоненциальную задержку (Exponential Backoff).
-   **Ошибка 4xx (Client Error):** Не повторять запрос (например, 401 Unauthorized требует рефреша токена, 404 — не имеет смысла повторять).
-   **Ошибка 5xx (Server Error) или Timeout:** Повторить запрос.
-   **Алгоритм:**
    1.  Попытка 1: Сразу.
    2.  Попытка 2: Через 2 секунды.
    3.  Попытка 3: Через 4 секунды.
    4.  Попытка 4: Через 8 секунд.
    -   *Максимум:* 3–5 попыток, чтобы не блокировать UI бесконечно.

## Глава 3. Локальное хранение данных

Мобильное приложение должно работать быстро и частично функционировать без сети.

### 3.1. Типы хранилищ
1.  **Key-Value Storage (UserDefaults / SharedPreferences):**
    -   *Для:* Простых настроек, флагов, токенов доступа.
    -   *Запрещено:* Хранить большие массивы данных или чувствительную информацию без шифрования.
2.  **Relational Database (SQLite, Room, CoreData):**
    -   *Для:* Структурированных данных с отношениями (пользователи, заказы, сообщения).
    -   *Оптимизация:* Использовать WAL (Write-Ahead Logging) режим для лучшей производительности записи.
    -   *Индексы:* Обязательно индексировать поля, по которым идёт поиск (например, `user_id`, `created_at`).
3.  **NoSQL / Document Store (Realm, Firebase Firestore):**
    -   *Для:* Гибких схем данных, быстрой синхронизации.
    -   *Плюсы:* Объектная модель (не нужен ORM-слой), встроенная реактивность.
4.  **File System:**
    -   *Для:* Кэширования изображений, видео, больших файлов.
    -   *Стратегия:* LRU (Least Recently Used) кэш для автоматического удаления старых файлов при нехватке места.

### 3.2. Шифрование данных на устройстве
Чувствительные данные (токены, персональная информация) должны быть зашифрованы.
-   **iOS:** Keychain Services. Данные шифруются аппаратно и привязываются к устройству.
-   **Android:** EncryptedSharedPreferences или Android Keystore System.
-   **SQLCipher:** Для шифрования всей SQLite базы данных одним паролем.

## Глава 4. Стратегия Offline-First

Приложение должно оставаться полезным при отсутствии соединения. Это требует сложной логики синхронизации.

### 4.1. Архитектура синхронизации
1.  **Local Cache as Source of Truth:** UI всегда рисует данные из локальной базы.
2.  **Sync Queue (Очередь синхронизации):**
    -   Все действия пользователя (создание заказа, лайк, сообщение), требующие сети, сохраняются в локальную таблицу `pending_operations`.
    -   Фоновый сервис (WorkManager на Android, BackgroundTasks на iOS) периодически пытается отправить очередь на сервер.
3.  **Разрешение конфликтов (Conflict Resolution):**
    -   *Сценарий:* Пользователь изменил профиль оффлайн, а сервер изменил его в это же время.
    -   *Стратегия "Last Write Wins":* Проще всего, но можно потерять данные.
    -   *Стратегия "Server Wins":* Данные сервера перезаписывают локальные.
    -   *Векторные часы:* Отслеживание версии каждого поля для точного слияния.

### 4.2. Индикация состояния
Пользователь должен понимать, что данные устарели или отправляются.
-   Показать значок «Оффлайн» в шапке.
-   Помечать локальные сообщения иконкой «часы» (отправляется), а подтверждённые сервером — «галочка».

## Глава 5. Безопасность мобильного приложения

Безопасность должна быть встроена на всех уровнях.

### 5.1. Аутентификация и Авторизация
-   **OAuth 2.0 / OIDC:** Стандарт для входа через соцсети или корпоративные аккаунты.
-   **JWT (JSON Web Tokens):**
    -   *Access Token:* Короткоживущий (5–15 минут). Используется для запросов.
    -   *Refresh Token:* Долгоживущий (дни/месяцы). Хранится в защищённом хранилище (Keychain/Keystore). Используется для получения новой пары токенов.
    -   *Ротация токенов:* При каждом использовании Refresh Token выдаётся новый. Если старый украден и использован злоумышленником, сервер detect'ит повторное использование и блокирует сессию.

### 5.2. Защита транспорта
-   **TLS 1.3:** Обязательно использовать современную версию протокола.
-   **SSL Pinning:** Приложение хранит хэш сертификата сервера и отвергает соединение, если сертификат не совпадает.
    -   *Зачем:* Защита от MITM-атак (Man-in-the-Middle), даже если пользователь установил свой корневой сертификат (например, корпоративный прокси).
    -   *Риск:* Усложняет обновление сертификатов на сервере. Нужно предусматривать механизм обновления пина через удалённую конфигурацию.

### 5.3. Защита кода и данных
-   **Obfuscation (ProGuard / R8):** Запутывание имен классов и методов, чтобы усложнить реверс-инжиниринг.
-   **Root/Jailbreak Detection:** Проверка устройства на наличие прав суперпользователя. При обнаружении — ограничение функционала (например, запрет платежей).
-   **Debug Detection:** Отключение приложения, если оно запущено в отладчике (защита от динамического анализа).

## Глава 6. Производительность и оптимизация

Пользователи удаляют приложения, которые работают медленно или греют телефон.

### 6.1. Время запуска (Startup Time)
-   **Cold Start:** Запуск с нуля. Должен занимать менее 2 секунд.
-   **Оптимизация:**
    -   Отложить инициализацию тяжелых SDK (аналитика, краш-репортеры) до момента, когда UI уже отображён.
    -   Использовать App Startup Library (Android) для упорядочивания инициализации.
    -   Минимизировать работу в `Application.onCreate` или `AppDelegate.didFinishLaunching`.

### 6.2. Работа с изображениями
Изображения — главный потребитель трафика и памяти.
-   **Форматы:** Использовать WebP или AVIF вместо PNG/JPEG (меньше вес при том же качестве).
-   **Кэширование:** Двухуровневое кэширование (Память + Диск). Библиотеки: Glide, Kingfisher, SDWebImage.
-   **Resize:** Загружать изображение размера, соответствующего view на экране. Не загружать фото 4000px для аватара 50px.
-   **Lazy Loading:** Загружать картинки только когда они появляются во viewport (списке).

### 6.3. Потребление батареи
-   **Геолокация:** Запрашивать точное местоположение только когда нужно. Использовать значительные изменения координат (Significant Location Change) вместо постоянного polling GPS.
-   **Таймеры:** Избегать частых таймеров в фоне. Использовать системные планировщики задач.
-   **Wake Locks:** Не удерживать экран включенным без необходимости.

### 6.4. Управление памятью
-   **Утечки памяти:** Часто возникают из-за циклических зависимостей (closure capturing self) или статических ссылкок на Context/View.
-   **Инструменты:** Instruments (iOS), Profiler (Android Studio).
-   **Bitmap:** Явно освобождать ресурсы больших изображений при уничтожении View.

## Глава 7. Масштабируемость бэкенда для мобильных приложений

Мобильное приложение не существует без сервера. Дизайн бэкенда влияет на клиент.

### 7.1. API Gateway
Единая точка входа для всех мобильных клиентов.
-   **Функции:** Роутинг, аутентификация, лимитирование запросов (Rate Limiting), трансформация ответов.
-   **Версионирование API:**
    -   *URL Versioning:* `/api/v1/users`, `/api/v2/users`.
    -   *Header Versioning:* `Accept-Version: 2.0`.
    -   *Правило:* Никогда не ломать обратную совместимость для старых версий приложения, которые ещё стоят у пользователей в сторах.

### 7.2. CDN (Content Delivery Network)
Статический контент (картинки, видео, конфиги) должен раздаваться через CDN (CloudFront, Cloudflare).
-   Снижает нагрузку на основной сервер.
-   Уменьшает задержку для пользователей в разных регионах.
-   Позволяет кэшировать контент на edge-серверах.

### 7.3. База данных и репликация
-   **Read Replicas:** Для мобильных приложений характерно много чтений и меньше записей. Настройте реплики для чтения, чтобы разгрузить master-базу.
-   **Sharding:** Если данных становится слишком много (например, история чатов), шардируйте базу по `user_id`.

## Глава 8. Тестирование и мониторинг

Качество мобильного приложения измеряется не только отсутствием багов, но и стабильностью в продакшене.

### 8.1. Уровни тестирования
1.  **Unit Tests:** Проверка логики ViewModel, UseCases, утилит. Быстрые, изолированные.
2.  **Integration Tests:** Проверка взаимодействия модулей (например, ViewModel + Repository).
3.  **UI Tests (E2E):** Автоматизация сценариев через Espresso (Android) или XCTest (iOS). Медленные, хрупкие, но необходимые для критических путей (логин, покупка).
4.  **Snapshot Tests:** Сравнение скриншотов UI с эталоном. Помогает ловить визуальные регрессии.

### 8.2. Мониторинг в продакшене
-   **Crashlytics / Sentry:** Сбор крашей и не фатальных ошибок.
    -   *Важно:* Включать сбор пользовательских событий (breadcrumbs), чтобы воспроизвести путь к ошибке.
-   **Performance Monitoring:**
    -   Время холодного старта.
    -   Замороженные кадры (Frozen Frames) — когда UI не отвечает более 16мс (для 60fps).
    -   Медленные запросы к сети.
-   **Аналитика:** Firebase Analytics, Amplitude. Отслеживание воронок конверсии.

### 8.3. Feature Flags (Флаги функций)
Механизм включения/выключения функциональности без выпуска новой версии приложения.
-   **Использование:**
    -   Постепенный релиз (Canary release): включить функцию для 10% пользователей.
    -   Экстренное отключение сломанной фичи.
    -   A/B тестирование интерфейсов.
-   **Реализация:** Конфиг загружается при старте приложения с сервера (Firebase Remote Config или собственное решение).

## Глава 9. Кейс: Дизайн архитектуры мессенджера

Рассмотрим применение вышеописанных принципов на примере создания чата.

### 9.1. Требования
-   Доставка сообщений в реальном времени.
-   Работа оффлайн (отправка при появлении сети).
-   Шифрование переписки.
-   Поддержка медиа (фото, голосовые).

### 9.2. Архитектурное решение
1.  **Клиент:** Clean Architecture.
    -   Domain: Entity `Message`, UseCase `SendMessage`.
    -   Data: Repository `ChatRepository`, Local DB (Room/CoreData), Remote Source (WebSocket).
2.  **Сеть:**
    -   WebSocket для получения новых сообщений.
    -   REST API для загрузки истории переписки (пагинация).
3.  **Локальное хранение:**
    -   Таблица `Messages` с полями: `id`, `conversation_id`, `body`, `status` (sending, sent, delivered, read), `timestamp`.
    -   Индекс по `conversation_id` + `timestamp` для быстрой выборки истории.
4.  **Синхронизация:**
    -   При отправке сообщение сразу пишется в БД со статусом `sending`.
    -   UI показывает сообщение мгновенно (Optimistic UI).
    -   Фоновый воркер отправляет пакет на сервер.
    -   При успехе статус обновляется на `sent`. При ошибке — на `failed` с кнопкой «Повторить».
5.  **Медиа:**
    -   Загрузка файла на Object Storage (S3) через Presigned URL.
    -   В чат отправляется только ссылка на файл.
    -   Кэширование файлов на диск с лимитом места (например, не более 500 МБ).

### 9.3. Проблемные места и решения
-   **Дублирование сообщений:** На стороне сервера использовать идемпотентность. Клиент генерирует `client_message_id`. Сервер проверяет, не обрабатывал ли он уже этот ID.
-   **Порядок сообщений:** Использовать серверное время для сортировки, но корректно обрабатывать рассинхронизацию часов устройства.
-   **Батарея:** Не держать WebSocket открытым, если приложение в фоне более 5 минут. Переключаться на Push-уведомления.

## Глава 10. Чек-лист перед релизом

Перед публикацией в App Store или Google Play проверьте следующие пункты системного дизайна:

1.  **Безопасность:**
    -   [ ] Токены хранятся в Keychain/Keystore?
    -   [ ] Включён SSL Pinning?
    -   [ ] Нет ли чувствительных данных в логах (Logcat/Console)?
2.  **Производительность:**
    -   [ ] Холодный старт < 2 сек на среднем устройстве?
    -   [ ] Нет ли утечек памяти при открытии/закрытии основных экранов?
    -   [ ] Изображения сжаты и кэшируются?
3.  **Надёжность:**
    -   [ ] Обработаны все состояния сети (Offline, Slow 3G)?
    -   [ ] Есть ли механизм отката Feature Flags?
    -   [ ] Настроены алерты на рост крашей (Crash-free users > 99.5%)?
4.  **Масштабируемость:**
    -   [ ] API поддерживает версионирование?
    -   [ ] Бэкенд выдержит нагрузочное тестирование (Load Testing) на пиковую аудиторию?
5.  **UX при ошибках:**

## Приложение А. Глоссарий терминов

-   **API (Application Programming Interface):** Набор правил для взаимодействия программ.
-   **CDN (Content Delivery Network):** Сеть серверов для быстрой доставки контента.
-   **CI/CD (Continuous Integration/Deployment):** Автоматизация сборки и выпуска приложений.
-   **DTO (Data Transfer Object):** Объект для передачи данных между слоями или сервисами.
-   **IDE (Integrated Development Environment):** Среда разработки (Xcode, Android Studio).
-   **JWT (JSON Web Token):** Стандарт для передачи утверждений между сторонами.
-   **Latency:** Задержка между запросом и ответом.
-   **ORM (Object-Relational Mapping):** Техника преобразования данных между несовместимыми типами систем (объекты кода и таблицы БД).
-   **RPC (Remote Procedure Call):** Протокол запроса удалённых процедур.
-   **SDK (Software Development Kit):** Набор инструментов для разработки под конкретную платформу.
-   **Throughput:** Пропускная способность системы (запросов в секунду).
-   **Uptime:** Время бесперебойной работы системы.
